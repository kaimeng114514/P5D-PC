# 本项目（P5D 静态重编译移植）与 Vita3K 模拟器的区别

> 本文只讨论技术路线差异，不评价任何项目的优劣。两者目标不同、成熟度不同，
> 且都要求用户使用**自己合法持有的正版游戏数据**。
>
> 相关：[README](../README.md) · [发布合规](RELEASE_COMPLIANCE.md) · [P5R Android 参考研究](P5R_ANDROID_REFERENCE.md)

---

## 0. 一句话总结

| | 本项目 | Vita3K |
|---|---|---|
| 本质 | **单个游戏（P5D / PCSH10109）的静态重编译 PC 移植** | **通用 PS Vita 模拟器** |
| 目标 | 把这一款游戏的原版二进制**翻译成本机原生代码**，由我们的兼容层驱动，最终原生画面/流程一致 | 在 PC 上**模拟整台 PS Vita**，按兼容性列表运行大量不同游戏 |
| 交付 | 单一引擎可执行文件 + 玩家自备游戏数据 + 本地 AOT/着色器缓存 | 模拟器可执行文件 + 玩家自备系统固件/游戏 |

---

## 1. CPU 执行方式

| | 本项目 | Vita3K |
|---|---|---|
| 方式 | **离线 AOT 静态重编译**：启动/首次运行前把原版 ARM/Thumb 全量翻译为 C++/x86-64 并编译为原生代码，执行路径无运行时代码生成；解释器仅作 fallback | **运行时动态重编译 / 解释器**：边执行边翻译（JIT），配合解释器兜底 |
| 产物 | 本机生成的 x86-64 原生代码缓存（不随仓库分发） | 运行时缓存 |
| 调试优势 | 每个 guest 函数对应一个 C++ 函数（可断点、可比对、可差分测试） | 通用 JIT 调试更复杂 |
| 覆盖范围 | 只覆盖本作需要的代码路径 | 面向大量游戏的通用代码路径 |

本项目的重编译器与差分测试（对比 Unicorn 参考语义）见：
`engine/recompiler/`、`tools/aot_difftest.py`、`tests/`。

## 2. 系统层（内核 / 服务）

| | 本项目 | Vita3K |
|---|---|---|
| 做法 | **HLE 兼容层**：只实现本作实际调用的系统 API（文件、内存、线程/fiber、同步原语、GXM、音频、输入、视频解码等），按 NID 接管 | **模拟 Vita 系统**：完整内核/服务框架（模块加载、SELF/ELF、文件系统、SceKernel、SceAppMgr、SceNgs、SceVideodec 等），面向通用兼容性 |
| 固件依赖 | 不需要固件；系统行为由我们按游戏需要实现 | 通常需要玩家自备 Vita 系统固件/模块 |
| 行为保真 | 以"让这款游戏跑通/画面一致"为目标，按需实现并记录证据 | 以"通用模拟正确性"为目标，覆盖面广 |
| 线程模型 | 运行时线程模型仍在演进：当前实验路径为 **一个 guest 线程 = 一个宿主线程 + 独立 CPU/内存上下文**，等待真阻塞 | 模拟 Vita 抢占式线程/内核对象语义 |

## 3. GPU / 图形

| | 本项目 | Vita3K |
|---|---|---|
| 做法 | **在 GXM API 层**把 `SceGxm*` 映射为 Vulkan 调用（对象 + 状态 + 绘制命令由我们回放），**不模拟 GPU 命令流** | 模拟 SceGxm/GPU：把 Vita 图形 API/命令翻译到宿主 OpenGL/Vulkan |
| 着色器 | 玩家数据里的 GSC/GXP **一次性离线翻译为 SPIR-V** 并本地缓存；运行时不编译着色器 | 运行时翻译着色器（缓存） |
| 渲染目标 | 原版游戏代码自己绘制（我们的后端只负责把 GXM 语义变成 Vulkan） | 原版游戏代码由模拟器绘制 |
| 取舍 | 性能/可打包性优先，只支持本作使用的 GXM 子集 | 兼容性优先，覆盖面大 |

## 4. 交付与发布形态

| | 本项目 | Vita3K |
|---|---|---|
| 仓库内容 | 仅引擎/工具/研究文档源码；**不含**游戏数据、密钥、固件、游戏衍生二进制 | 模拟器源码；不含游戏 |
| 运行所需 | 玩家自备 eboot/SELF 与 data.cpk/vita.cpk（本机读取） | 玩家自备固件与游戏 |
| 分发形态 | 单一 `P5D_Engine.exe` + 本地缓存（`cache/recomp`、`cache/shaders`、`cache/pipelines`） | 模拟器 + 用户环境 |
| 合规扫描 | `tools/release_audit.py` 强制检查（禁止游戏文件/游戏衍生数据） | 社区合规约定 |

## 5. 成熟度与现状（诚实说明）

- **Vita3K**：多年社区项目，兼容性广、已有大量可玩游戏，是 Vita 生态最重要的通用模拟器之一。
- **本项目**：实验性静态重编译移植，**目前尚未进入渲染帧循环**（`framectr=0`），
  已完成 AOT 重编译器、HLE、GXM→Vulkan 后端与大量运行时语义分析；
  所有进展与证据（含失败与纠正）记录在 [P5D_MASTER.md](P5D_MASTER.md)。
  当前不做"能玩"承诺；目标是把"原版二进制 + 我们的 HLE + 原版代码绘制"这条路线走通。

## 6. 为什么会选择"静态重编译移植"而不是"模拟器"

1. **性能与启动**：AOT 后是原生 x86-64 代码，无运行时翻译开销。
2. **打包与移动端**：单一可执行文件 + 本地缓存的结构更容易裁剪、移植到 Android。
3. **可调试性**：每个 guest 函数是普通 C++ 函数，可用本机工具链断点/差分测试（本项目已有 Unicorn 差分测试）。
4. **确定性**：不依赖运行时 JIT 缓存状态；同样的输入产生同样的执行序列（便于回归）。
5. **代价**：只能服务这一款游戏；系统/GPU 覆盖是"按需实现"，工作量集中在运行时语义上，
   进展速度远慢于通用模拟器。

## 7. 两者的共性

- 都要重新实现 Sce 系统 API（HLE / 模拟服务）；
- 都要把 GXM 图形调用翻译到宿主 GPU；
- 都需要玩家自备游戏数据；
- 都必须处理 ARM 代码执行、内存映射、线程/同步语义。

区别在于：**通用模拟器追求"像 Vita"；本项目追求"这款游戏在 PC 上原生地跑起来"**。
